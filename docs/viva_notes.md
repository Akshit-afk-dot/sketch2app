# Viva notes: 30 likely questions, answered from this codebase

Numbers are in [results.md](results.md) and [data_report.md](data_report.md) (generated by scripts; quote
from there, not from memory). File references point to where each answer lives in the code.

## Problem and architecture

**1. What does the system do, end to end?**
Ink strokes -> our stroke recognizer groups and classifies them into UI elements and arrows -> ML Kit reads
the handwritten labels -> a layout model turns the element list into a compact UI spec (JSON) -> a Flutter
interpreter renders it live, and a code generator exports a Flutter project. All on the device (DESIGN.md §1).

**2. Why not one big end-to-end model (image in, code out)?**
Each stage can then be tested, measured and replaced on its own; each has a deterministic fallback, so a
failure degrades quality instead of breaking the demo. It also fits a phone: a 2M-parameter recognizer and a
2B-effective-parameter LLM writing ~120-token specs, rather than a large vision-language model writing code.

**3. Why strokes and not a rendered image?**
Ink arrives already segmented into strokes with order and timing. An outline is one fast closed stroke; a word
is many small strokes close in time; that information is lost in pixels. A sequence of ~100 strokes is also
much cheaper than a CNN on a megapixel canvas (`ml/s2a/recognizer/features.py` docstring).

**4. Why a UI spec instead of generating Dart directly?**
(a) Tokens: generated Dart for the same apps costs ~3.9x the spec's tokens (results.md §3), and decode time
is proportional to output tokens. (b) A closed vocabulary can be validated and repaired; free-form code
cannot be compiled on the phone. (c) One spec drives both the live preview and the export. (d) Trees can be
compared with tree-edit distance; code cannot (DESIGN.md §2).

**5. Why a direct interpreter for the preview instead of rfw?**
The vocabulary is closed (17 node types) and typed with Dart sealed classes, so the interpreter's `switch` is
exhaustive; rfw would add a translation layer and still need local widgets for state and navigation; its
strength (server-pushed UI) does not apply offline (DESIGN.md §3).

## Data

**6. Where does training data come from, and why is it all programmatic?**
RICO's semantic hierarchies (66k real Android screens) give real structure and text; we convert them to specs
(`rico_convert.py`) and draw each spec as a synthetic sketch (`sketch_layout.py`, `synth.py`). No LLM-generated
data: labels are exact by construction, and the dataset is reproducible from a seed.

**7. How do you avoid leakage between train and test?**
Splits are by app (sha1 of the package name), so no app's screens appear in two splits (`build_dataset.py`).
Real sketches are split by participant, frozen at first import (`collected.py`).

**8. Your sketches are synthetic. Why should results transfer to real drawings?**
The noise model covers the main human variations (correlated jitter, overshoot, re-traced and broken strokes,
rotation/shear, sloppy alignment, random stroke order, realistic timing). The honest answer is in the real
test set from Collect mode, reported separately in results.md, plus fine-tuning on real sketches.

**9. Why lay out sketches yourself instead of using RICO's pixel positions?**
Our spec simplifies the app; drawing at the app's positions would leave gaps and mismatches. Our own layout
guarantees sketch == gold spec; anything changed to fit (shortened labels, dropped overflow) changes the gold.

**10. RICO has no dividers and few bottom navs; how does the model learn them?**
Legend-coverage augmentation inserts them (and FABs, radios, switches) before sketching, with labels taken
from the corpus (`augment.py`). Counts before/after are in the data report.

**11. Why XY-cut for converting RICO?**
Greedy row grouping flattened nested layouts (thumbnail + title/description became one row). Recursive XY-cut,
a classic document-layout algorithm, recovers rows of columns from component bounds.

## Stroke recognizer

**12. Describe the recognizer.**
Per stroke: 32 arc-length-resampled points through a 1D CNN, plus 16 geometric/timing features; a 4-layer
transformer over all strokes with 2D sinusoidal position and drawing-order encodings; heads for stroke class,
element type, and pairwise same-group affinity. 1.98M parameters, 8 MB ONNX (`model.py`).

**13. Why a transformer over strokes?**
A stroke's meaning depends on its neighbours (a rectangle is a button if text is inside, an image if an X is
inside). Self-attention lets every stroke attend to every other.

**14. How are strokes grouped into elements without knowing how many there are?**
The model predicts, for every pair of strokes, whether they belong together; average-linkage clustering
merges clusters while their mean affinity exceeds 0.5 (`decode.py`). Average linkage resists chaining: one
wrong confident pair cannot glue two elements together (connected components would).

**15. Why no bounding-box regression head?**
An element's box is exactly the union of its strokes, which we have after grouping.

**16. How do you know the phone runs the same model as Python?**
Three checks: PyTorch vs ONNX Runtime outputs (max |diff| in results.md); Python vs Dart features and
decoder on fixtures (`app/test/recognizer_parity_test.dart`); and an in-app self-test that runs a fixture through
ORT on the device and reports the difference (Settings > Recognizer self-test).

**17. What is the baseline and how much better is the model?**
The rule-based recognizer implements the legend literally (`heuristic_recognizer.dart`); both are scored by
the same metric code on the same 1,000 test sketches (results.md §1).

## Layout model

**18. What exactly does the LLM see and produce?**
A compact element list: one line per element with type, frame-relative integer-percent box and label, plus
resolved links "L 3>S2" (`prompt.py`); it outputs the canonical spec JSON. Arrows are resolved to source
element and target screen geometrically before the LLM sees them.

**19. Why fine-tune instead of prompting?**
The base model with 3 examples is a reported baseline (results.md §2). Fine-tuning teaches the exact format,
id rule and our layout conventions, and is cheap with LoRA.

**20. What is LoRA and why these hyper-parameters?**
Low-rank adapters: freeze the base weights and learn delta W = B A with rank r (16), scaled by alpha/r (32/16).
Adapters on all linear layers give the most capacity per parameter; lr 2e-4 is the standard LoRA rate; early
stopping on validation tree similarity selects the checkpoint by the metric we report.

**21. What is QLoRA / quantization here?**
QLoRA trains LoRA adapters on top of a 4-bit (NF4) frozen base, so a 16 GB T4 can fine-tune Gemma 4 E2B.
On the phone, LiteRT-LM runs the merged model with low-bit weights; the stock E2B bundle mixes 2/4/8-bit.

**22. Why is training input deliberately noisy?**
At test time the input comes from the recognizer and handwriting reader, which make mistakes. We measure the
trained recognizer's errors on val (miss rates per type, confusions, false positives, box jitter) and replay
them on gold element lists (`noise.py`); otherwise the model never learns to recover.

**23. What happens when the LLM outputs invalid JSON?**
Validate -> repair (strip prose, close truncated JSON, remove trailing commas, drop unknown keys/types, fix
one-option radios, drop dangling links) -> retry at temperature 0 -> rule-based layout (`repair.dart`,
`llm_layout.dart`). With llama.cpp in LAN mode, decoding is grammar-constrained to the JSON Schema.

**24. Why Gemma 4 E2B, and why Qwen3.5-0.8B as fallback?**
E2B has ~2B effective parameters with per-layer embeddings, runs on LiteRT-LM on phones, and is Apache-2.0.
Qwen3.5-0.8B is ~3x smaller for weak devices; both are supported by LiteRT-LM via flutter_edge_ai.

## Evaluation

**25. Explain each metric.**
Detection P/R/F1 at IoU >= 0.5 (any-type and typed); stroke accuracy; JSON/schema validity rate; normalized
tree-edit similarity 1 - TED/max(|T|) (APTED, structure only); element-type F1 over leaf types; link F1 over
apps that have links; label accuracy; latency per stage; model size; flutter analyze pass rate of exports.

**26. Why tree-edit distance?**
A UI spec is a tree; TED counts the minimum insertions, deletions and relabellings to turn one into the other,
so it rewards getting most of the structure right instead of all-or-nothing exact match.

**27. What were the ablations?**
Noise augmentation on/off for the layout model; recognizer with/without real-data fine-tuning; spec vs direct
Dart (tokens; latency). Status of each is in results.md §5.

## Engineering and limitations

**28. How is offline guaranteed?**
ML Kit's language pack is downloaded once; the recognizer ships in the APK; the layout model is pushed to
app storage; every stage has an offline rule-based fallback. Tested in airplane mode (docs/demo_script.md).

**29. What are the main limitations?**
Icons are generic (the legend cannot express which icon); no styling, colours or custom fonts; English
handwriting only; synthetic-to-real gap (measured on Collect data); small Collect set; on-device LLM needs
Android 11+ arm64 and a few GB of storage/RAM.

**30. What would you do next?**
More real sketches and fine-tuning; GRPO with a reward for schema validity, tree similarity and box IoU
(planned stretch); an icon vocabulary in the legend; styling attributes in the spec; iOS build.
